# ROOMIE --- Database Schema and Data Model

**Version:** 1.5\
**Date:** 19 November 2026\
**Database:** PostgreSQL\
**ORM:** SQLAlchemy 2.x\
**Migrations:** Alembic

**Changes in 1.5** (migration `0005`, see section 11):

-   `accommodation_listings`: `brokerage_payable_to`, `facilities` and
    `authority_declared_at`, with checks that brokerage names who receives
    it, that only an authorised agent may collect it, that facilities come
    from a fixed list, and that a property listing records its creator's
    declaration of authority (section 3.10).
-   `listing_authority_verifications`: `tenant_permission_basis` and
    `rental_agreement_valid_until` (section 3.7).
-   `listing_images`: `content_type`, `width`, `height`, `size_bytes`
    (section 3.12).
-   `listing_interests`: `acknowledged_brokerage_amount`, `responded_at`,
    `updated_at` and an index on `user_id` (section 3.13).
-   New append-only table `listing_changes` (section 3.24).

**Changes in 1.4** (migration `0004`, see section 10):

-   `matches.compatibility_score` may be empty (section 3.15).
-   New unique partial index `uq_notifications_new_match`: one "new match"
    notification per person per match (section 3.20).
-   Section 5 now describes the discovery visibility rule and the match
    creation steps exactly as implemented, including the pair lock.

**Changes in 1.3** (migration `0003`, see section 9 for the reasoning):

-   `localities` and `societies` became a curated, verified directory. Both
    gained `name_key`, `verification_status`, `verified_at`, `verified_by`
    and `source_note`. `localities` also gained `description`,
    `created_at` and `updated_at`.
-   New column `societies.community_type`.
-   Duplicate rules changed. Society names are now unique across the
    whole directory (previously only within one locality), and both tables
    compare the normalised `name_key` rather than the raw name.
-   New append-only table `directory_events` (section 3.23) records every
    change.
-   A society is public only when it **and** its locality are both verified
    and active (section 5, "Directory visibility").

**Changes in 1.2:** two tables for signing in, `sessions` and
`account_tokens` (sections 3.21 and 3.22), and `users.terms_accepted_at`.
No existing table or rule changed.

**Changes in 1.1** (see section 8 for the reasoning):

-   Three listing creator types: property owner, existing tenant,
    authorised agent.
-   Listings carry two independent statuses: a creator-controlled
    lifecycle status and an admin-controlled moderation status.
-   Verification is three independent record types: identity, student and
    listing authority. The single `student_verifications` design of 1.0 is
    replaced.
-   New tables: `identity_verifications`,
    `listing_authority_verifications`, `verification_documents`,
    `review_events`.
-   Brokerage disclosure columns on listings.
-   The default user role is `MEMBER` (not every user is a student).

## 1. Design conventions

-   UUID primary keys for main entities, generated by the database.
-   `TIMESTAMPTZ` for timestamps.
-   Money is stored as **whole Indian rupees** in `INTEGER` columns.
-   Foreign keys and database constraints enforce rules, not application
    checks alone.
-   `created_at` and `updated_at` on mutable records.
-   Controlled values (roles, statuses, types) are stored as `VARCHAR`
    with a `CHECK` constraint listing the allowed values. This is as safe
    as a native PostgreSQL enum but far easier to change in a migration.
-   Soft status transitions for accounts, matches and listings where
    history matters.
-   Files live in private object storage. PostgreSQL stores only an object
    key and metadata, never the file itself.
-   Email addresses are stored in lower case, enforced by a constraint, so
    uniqueness is case-insensitive.
-   Every constraint and index has an explicit, predictable name so
    migrations can refer to it.

### 3.5 `societies`

One named residential development (an apartment complex or a villa
community) inside a locality.

| Column              | Type         | Constraints                        |
| ------------------- | ------------ | ---------------------------------- |
| id                  | UUID         | PK                                 |
| locality_id         | UUID         | FK localities.id, NOT NULL         |
| name                | VARCHAR(180) | NOT NULL                           |
| name_key            | VARCHAR(180) | NOT NULL, not empty                |
| community_type      | VARCHAR(30)  | nullable; required to verify       |
| address             | TEXT         | nullable, never public             |
| latitude            | NUMERIC(9,6) | nullable, approximate, not public  |
| longitude           | NUMERIC(9,6) | nullable, approximate, not public  |
| description         | TEXT         | nullable, public                   |
| is_active           | BOOLEAN      | NOT NULL, default true             |
| verification_status | VARCHAR(20)  | NOT NULL, default `UNVERIFIED`     |
| verified_at         | TIMESTAMPTZ  | nullable                           |
| verified_by         | UUID         | FK users.id, nullable              |
| source_note         | TEXT         | nullable, administrators only      |
| created_at          | TIMESTAMPTZ  | NOT NULL                           |
| updated_at          | TIMESTAMPTZ  | NOT NULL                           |

Unique: `name_key`, across the **whole** directory. The same complex
filed under two neighbouring localities would be a duplicate.

community_type: `APARTMENT_COMPLEX`, `VILLA_COMMUNITY`. Plotted layouts
(land sold as plots) are not societies and are not added.

Rules shared by both tables:

-   verification_status: `UNVERIFIED`, `VERIFIED`. Every record starts
    `UNVERIFIED`. Check: a `VERIFIED` record has `verified_by` and
    `verified_at`.
-   `name_key` is the name in lower case with every run of punctuation or
    spaces turned into one space, so "Abode-Valley" and "abode  valley"
    collide. The application sets it from `name`, and the migration
    filled it for existing rows with the same rule in SQL. It cannot
    catch real spelling differences ("Guduvanchery" and "Guduvancheri");
    an administrator must look for those.
-   Changing a core field of a verified record (locality: name, city,
    state; society: name, locality, community type, address) returns it to
    `UNVERIFIED`. The changed record must be checked again before it is
    shown.
-   Records are created and changed only by administrators, through the
    admin API or the `app.scripts.directory` command. Members cannot add
    them.
-   Records are switched off with `is_active = false`, not deleted, so
    members' saved choices keep pointing at them.

### 3.6 `user_society_preferences`

| Column     | Type        | Constraints         |
| ---------- | ----------- | ------------------- |
| user_id    | UUID        | PK, FK users.id     |
| society_id | UUID        | PK, FK societies.id |
| priority   | SMALLINT    | NOT NULL, > 0       |
| created_at | TIMESTAMPTZ | NOT NULL            |

Unique: `(user_id, priority)`, so two societies cannot share a rank.

A member can save only societies that are currently public. A saved
society that later stops being public (it was switched off or
unverified) **stays saved**. The API marks it `available: false`, the app
shows it as "No longer available", and it does not count towards a
complete profile. Nothing is deleted on the member's behalf.

### 3.7 Verification: three independent record types

Roomie never has a single "verified" flag. There are three separate
checks, each with its own table, its own status and its own review
history:

| Check                 | Confirms                                              | Belongs to |
| --------------------- | ----------------------------------------------------- | ---------- |
| Identity              | The person is who they say they are                   | a user     |
| Student               | The person is currently enrolled at an institution    | a user     |
| Listing authority     | The person has the right to list one specific property | a listing  |

They are independent. A property owner can pass identity and listing
authority without being a student. A student can pass identity and
student verification without any right to list a property. An agent can
pass identity and listing authority without being a student.

All three share the same review columns and the same statuses:
`PENDING`, `APPROVED`, `REJECTED`, `NEEDS_RESUBMISSION`. **The absence of
a row means "not verified".**

#### `identity_verifications`

| Column        | Type        | Constraints               |
| ------------- | ----------- | ------------------------- |
| id            | UUID        | PK                        |
| user_id       | UUID        | FK users.id, UNIQUE       |
| status        | VARCHAR(20) | NOT NULL, default PENDING |
| submitted_at  | TIMESTAMPTZ | NOT NULL                  |
| reviewed_by   | UUID        | FK users.id, nullable     |
| reviewed_at   | TIMESTAMPTZ | nullable                  |
| reviewer_note | TEXT        | nullable                  |
| created_at    | TIMESTAMPTZ | NOT NULL                  |
| updated_at    | TIMESTAMPTZ | NOT NULL                  |

#### `student_verifications`

The columns above, plus:

| Column           | Type         | Constraints |
| ---------------- | ------------ | ----------- |
| method           | VARCHAR(20)  | NOT NULL    |
| institution_name | VARCHAR(180) | NOT NULL    |
| valid_until      | DATE         | nullable    |

Methods: `COLLEGE_EMAIL`, `DOCUMENT`, `MANUAL`. Enrolment ends, so an
approval may carry a `valid_until` date after which it no longer counts.

#### `listing_authority_verifications`

One per listing (`listing_id` is UNIQUE), replacing `user_id`. Only
`EXISTING_ACCOMMODATION` listings have one. The review columns above,
plus the owner-authorisation fields:

| Column                    | Type         | Constraints                      |
| ------------------------- | ------------ | -------------------------------- |
| listing_id                | UUID         | FK accommodation_listings.id, UNIQUE |
| owner_name                | VARCHAR(120) | nullable, private                |
| owner_contact             | VARCHAR(255) | nullable, private                |
| owner_confirmation_status | VARCHAR(20)  | NOT NULL, default NOT_REQUIRED   |
| owner_confirmed_by        | UUID         | FK users.id, nullable            |
| owner_confirmed_at        | TIMESTAMPTZ  | nullable                         |
| owner_confirmation_note   | TEXT         | nullable                         |

Owner confirmation statuses: `NOT_REQUIRED`, `PENDING`, `CONFIRMED`,
`DENIED`. "Confirmation" means a Roomie administrator contacted the owner
directly, using details the administrator checked independently, and the
owner confirmed. A document supplied by the agent is never enough on its
own.

**What each creator type must provide** before listing authority can be
approved (enforced by the verification service):

| Creator type     | Required                                                                 |
| ---------------- | ------------------------------------------------------------------------ |
| Property owner   | Approved identity verification and an `OWNERSHIP_PROOF` document          |
| Existing tenant  | `RENTAL_AGREEMENT` document, its end date, and a recorded permission basis; `LANDLORD_PERMISSION` document when the agreement does not itself allow sharing |
| Authorised agent | Approved identity verification, `OWNER_AUTHORIZATION` document, and owner confirmation `CONFIRMED` |

Two further columns on `listing_authority_verifications`, filled in by
the reviewer when approving a tenant (version 1.5):

| Column                       | Type        | Constraints                         |
| ---------------------------- | ----------- | ----------------------------------- |
| tenant_permission_basis      | VARCHAR(30) | nullable; `AGREEMENT_PERMITS_SHARING` or `LANDLORD_PERMISSION` |
| rental_agreement_valid_until | DATE        | nullable                            |

A tenant's listing authority is treated as lapsed (and the listing is
hidden) once `rental_agreement_valid_until` has passed.

### 3.8 `verification_documents`

Metadata for evidence files. The file itself is in **private** object
storage; this table holds only a reference.

| Column                            | Type         | Constraints                  |
| --------------------------------- | ------------ | ---------------------------- |
| id                                | UUID         | PK                           |
| identity_verification_id          | UUID         | FK, nullable                 |
| student_verification_id           | UUID         | FK, nullable                 |
| listing_authority_verification_id | UUID         | FK, nullable                 |
| document_type                     | VARCHAR(30)  | NOT NULL                     |
| storage_key                       | TEXT         | NOT NULL, UNIQUE, private    |
| original_filename                 | VARCHAR(255) | nullable                     |
| content_type                      | VARCHAR(100) | NOT NULL                     |
| size_bytes                        | INTEGER      | NOT NULL, > 0                |
| sha256                            | CHAR(64)     | nullable                     |
| uploaded_by                       | UUID         | FK users.id, NOT NULL        |
| created_at                        | TIMESTAMPTZ  | NOT NULL                     |
| deleted_at                        | TIMESTAMPTZ  | nullable                     |

Check: **exactly one** of the three verification columns is set.

Document types: `GOVERNMENT_ID`, `STUDENT_ID`, `ENROLMENT_PROOF`,

### 3.10 `accommodation_listings`

| Column               | Type         | Constraints                  |
| -------------------- | ------------ | ---------------------------- |
| id                   | UUID         | PK                           |
| owner_id             | UUID         | FK users.id, NOT NULL        |
| listing_type         | VARCHAR(30)  | NOT NULL                     |
| creator_type         | VARCHAR(20)  | conditional, see below       |
| title                | VARCHAR(180) | NOT NULL                     |
| description          | TEXT         | NOT NULL                     |
| society_id           | UUID         | FK societies.id, conditional |
| total_rent           | INTEGER      | nullable                     |
| rent_per_person      | INTEGER      | NOT NULL, > 0                |
| deposit              | INTEGER      | nullable, >= 0               |
| brokerage_applicable | BOOLEAN      | conditional, see below       |
| brokerage_amount     | INTEGER      | conditional, see below       |
| brokerage_payable_to | VARCHAR(30)  | conditional, see below       |
| brokerage_note       | VARCHAR(255) | nullable                     |
| bedroom_count        | SMALLINT     | nullable, > 0                |
| available_bedrooms   | SMALLINT     | nullable, > 0                |
| furnishing           | VARCHAR(20)  | nullable                     |
| facilities           | VARCHAR(30)[] | NOT NULL, default empty     |
| authority_declared_at | TIMESTAMPTZ | required for properties      |
| available_from       | DATE         | NOT NULL                     |
| current_group_size   | SMALLINT     | NOT NULL, >= 0               |
| required_roommates   | SMALLINT     | NOT NULL, > 0                |
| lifecycle_status     | VARCHAR(20)  | NOT NULL, default DRAFT      |
| moderation_status    | VARCHAR(20)  | NOT NULL, default PENDING    |
| created_at           | TIMESTAMPTZ  | NOT NULL                     |
| updated_at           | TIMESTAMPTZ  | NOT NULL                     |

`owner_id` is the user who created the listing (the account that owns the
record), whatever their creator type.

Listing types: `EXISTING_ACCOMMODATION`, `LOOKING_TO_RENT_TOGETHER`.\
Creator types: `PROPERTY_OWNER`, `EXISTING_TENANT`, `AUTHORIZED_AGENT`.\
Furnishing: `UNFURNISHED`, `SEMI_FURNISHED`, `FULLY_FURNISHED`.

`rent_per_person` holds the rent for an existing accommodation and the
budget per person for a search post.

**Two independent statuses.** They are separate columns and must never be
merged into one:

| Column            | Controlled by | Values                                      |
| ----------------- | ------------- | ------------------------------------------- |
| lifecycle_status  | The creator   | `DRAFT`, `ACTIVE`, `FILLED`, `CLOSED`       |
| moderation_status | Administrators | `PENDING`, `APPROVED`, `REJECTED`, `SUSPENDED` |

**Visibility rule.** A listing is publicly discoverable **only** when
`lifecycle_status = 'ACTIVE' AND moderation_status = 'APPROVED'`.
Pending, rejected and suspended listings never appear in public
discovery, whatever their lifecycle status. The reason for a rejection or
suspension is the `note` on the matching `review_events` row and is shown
only to the creator and to administrators.

An `EXISTING_ACCOMMODATION` listing may only be approved once its listing
authority verification is `APPROVED`. This is how unauthorised brokers
are kept out: no verified authority, no public listing.

Conditional checks, enforced by database constraints:

-   `EXISTING_ACCOMMODATION`: `creator_type`, `society_id` and
    `brokerage_applicable` are all required.
-   `LOOKING_TO_RENT_TOGETHER`: `creator_type` and `brokerage_applicable`
    must be null (it is a request, not a property). Preferred societies
    are in `listing_society_preferences`.
-   Brokerage must be disclosed either way. If `brokerage_applicable` is
    true, `brokerage_amount` is required and positive; otherwise it must
    be null.
-   `available_bedrooms <= bedroom_count` when both are present.
-   When brokerage applies, `brokerage_payable_to` (`LISTING_CREATOR` or
    `THIRD_PARTY_AGENT`) is required; otherwise it must be null.
    `LISTING_CREATOR` is allowed only when `creator_type =
    'AUTHORIZED_AGENT'`: an owner or tenant charging brokerage would be
    acting as an unauthorised broker.
-   `facilities` may only contain known values (Wi-Fi, air conditioning,
    washing machine, fridge, kitchen, water purifier, geyser, power backup,
    lift, parking, security, housekeeping).
-   A property listing must have `authority_declared_at`: the moment its
    creator declared they may offer it. The declaration is never treated as
    evidence.

**Full visibility rule (Phase 6).** Besides `ACTIVE` and `APPROVED`, a
listing is shown only when its creator's account is active, its society
(or, for a search post, at least one preferred society) and that
society's locality are verified and switched on, a tenant's rental
agreement has not ended, and neither person has blocked the other. The
rule lives in one place: `app/repositories/listings.py`.

**Changes send a live listing back for review.** Editing an approved
listing, changing its photos or changing its brokerage sets
`moderation_status` back to `PENDING`, hiding it until an administrator
looks again. Changing the society or the creator type also reopens the
listing authority check. Every change is written to `listing_changes`.

Do not store unit numbers or exact addresses in any listing field.

### 3.23 `directory_events`

The change history of the directory: one row for every create, edit,
verification and (de)activation of a locality or society. Rows are never
edited or deleted.

| Column      | Type        | Constraints                                  |
| ----------- | ----------- | -------------------------------------------- |
| id          | UUID        | PK                                           |
| sequence    | BIGINT      | NOT NULL, generated always as identity       |
| locality_id | UUID        | FK localities.id, nullable, cascade          |

| actor_id    | UUID        | FK users.id, nullable                        |

| changes     | JSONB       | nullable                                     |
| note        | TEXT        | nullable                                     |
| created_at  | TIMESTAMPTZ | NOT NULL                                     |

Check: exactly one of `locality_id` and `society_id` is set.

-   `actor_id` is the administrator. It is empty only for changes made by
    a server-side script, which then names itself in `note` (for example
    the candidate import).
-   `changes` holds edits as `{"field": {"from": old, "to": new}}`.
-   History is read in `sequence` order. `created_at` alone is not enough,
    because every change made in one transaction gets the same time.
-   The cascade only matters for unreferenced development samples, which
    the `retire-samples` command deletes. Real records are switched off,
    never deleted.

## 5. Data integrity and transaction rules

### Directory visibility

A society is shown to members (in search, on detail pages and as a
choice) only when **all four** hold:

1.  the society is `VERIFIED`,
2.  the society is active,
3.  its locality is `VERIFIED`,
4.  its locality is active.

A locality is listed publicly only when it is verified and active. The
rule lives in one place in code (`is_listed` on the models, used by
`app/repositories/directory.py`), so every public endpoint applies it the
same way. Anything else answers 404, as if it did not exist.

### Directory changes

1.  Begin transaction.
2.  Check for a duplicate `name_key`. Refuse with a message naming the
    existing record (and its locality).
3.  Apply the change. If a core field of a verified record changed, set
    it back to `UNVERIFIED`.
4.  Insert a `directory_events` row with the actor, action, changes and
    note. A note is required to verify or unverify.
5.  Commit.

To verify a society, its `community_type` must be known.

### Listing moderation

1.  Begin transaction.
2.  For an `EXISTING_ACCOMMODATION` listing being approved, confirm its
    listing authority verification is `APPROVED`. Refuse otherwise.
3.  Update `moderation_status`.
4.  Insert a `review_events` row with the actor, old status, new status
    and note. A note is required when rejecting or suspending.
5.  Commit.

### Verification review

1.  Begin transaction.
2.  For listing authority, confirm the creator type's requirements in
    section 3.7 are met before approving. Refuse otherwise.
3.  Update `status`, `reviewed_by`, `reviewed_at`, `reviewer_note`.
4.  Insert a `review_events` row.
5.  Commit.

### Discovery visibility

A member may see another member (in discovery, on a full profile, and as
the target of a like or pass) only when the other member:

1.  is not themselves,
2.  has `account_status = ACTIVE` and `role = MEMBER`,
3.  has `email_verified_at` set,
4.  has a student profile with `profile_completed = true`, and
5.  has no `blocks` row with the viewer, in either direction.

Discovery also leaves out anyone the viewer already has a `swipes` row
for. The rule is written once, in `app/repositories/discovery.py`. A
matched person stays visible to their match while both accounts are open
and neither has blocked the other. Everything else answers 404.

### Mutual match creation

As implemented in `app/services/matching.py`:

1.  Begin transaction.
2.  Check the actor: published profile and confirmed email.
3.  Take a transaction advisory lock on the normalised pair:
    `pg_advisory_xact_lock(hashtextextended('roomie-pair:<low>:<high>', 0))`.
    Any other request about the same two people waits here.
4.  Check the target is still visible (rule above). Refuse with 404.
5.  Read the actor's existing decision. Same action: do nothing more.
    Different action: refuse (409).
6.  Insert the swipe, `ON CONFLICT (actor_id, target_id) DO NOTHING`.
7.  If it is a like and the target's like towards the actor exists:
    insert the match with the pair ordered,
    `ON CONFLICT (user_one_id, user_two_id) DO NOTHING`; insert its
    conversation, `ON CONFLICT (match_id) DO NOTHING`; insert one
    `NEW_MATCH` notification for each person, `ON CONFLICT` on the partial
    unique index `DO NOTHING`.
8.  Commit, which releases the lock.

Why the lock: in PostgreSQL's default isolation, two simultaneous likes
could each look for the other's like before it is committed, both see
nothing, and no match would be created. With the lock, the second request
runs only after the first commits, and then sees it (`READ COMMITTED` reads
committed data at every statement). The unique constraints are the second
line of defence: even without the lock, duplicates are impossible.

### Listing interest

-   The listing must be publicly visible (section 3.10).
-   The creator cannot express interest in their own listing.
-   No duplicate interest.
-   Check blocks and account status.

### Message creation

-   The conversation exists and its match is active.
-   The sender is a participant.
-   Neither participant has blocked the other.
-   Persist the message before broadcasting it.

## 6. Privacy and retention

-   Verification evidence lives in private object storage, reachable only
    by authorised administrators and the uploader.
-   `storage_key`, `owner_name`, `owner_contact`, `password_hash`, any
    `token_hash`, `date_of_birth` and society `address` never appear in public API
    responses.
-   Exact residential addresses are never exposed.
-   Roomie never collects rent, deposits or brokerage, and nobody may
    collect payments in Roomie's name. No table stores payment details.
-   Define deletion and retention periods for accounts, messages, reports
    and verification evidence before launch.
-   `review_events` is the audit log for verification and moderation
    decisions and is append-only.
-   Society `address`, `latitude`, `longitude` and every `source_note` are
    for administrators only. Public directory responses contain only a
    society's name, locality, community type and description.
-   `directory_events` is the audit log for the directory and is
    append-only.

## 8. Design decisions in version 1.1

**Three verification tables rather than one.** A single table with a
"type" column was considered. Separate tables were chosen because the
three checks attach to different things (two to a user, one to a
listing), carry different fields, and must never be confused. With
separate tables the database itself guarantees, for example, that a
listing authority record always points at a listing. The shared review
columns are defined once in code and reused.

**One `verification_documents` table and one `review_events` table.**
These hold the same information whichever check they belong to, so one
table each avoids three near-identical copies. A constraint ensures every
row belongs to exactly one subject.

**Two status columns on listings.** The creator and the administrators
answer different questions ("is this still available?" and "is this
allowed to be shown?"). One combined status could not express, say, a
listing the creator has marked filled that was earlier suspended.

**Creator type lives on the listing, not on the user.** The same person
can own one property and be a tenant in another. Authority is therefore
verified per listing.

## 9. Design decisions in version 1.3

**Verified and active are separate.** "Is this information correct?" and
"should students see it right now?" are different questions. An accurate
record can be switched off temporarily, and a newly entered record stays
hidden until someone has checked it. Every record starts unverified, so
nothing reaches students by accident.

**The locality must be public too.** A society inside an unverified or
switched-off area is hidden. This lets an administrator hide a whole area
with one change, and stops a society appearing under an area name nobody
has checked.

**Duplicates are compared on a normalised key, and society names are
unique everywhere.** Spelling the same name with different punctuation
or capitals ("Abode-Valley", "abode valley") is the most common way
duplicates appear, and a database constraint catches it every time. The
old rule allowed the same society name in two localities, but nearby
areas around SRM overlap, so one complex filed under two areas was a real
risk. Genuinely different spellings still need a person to notice them;
the admin search helps with that.

**Editing a verified record unverifies it.** Otherwise someone could
verify a correct record and later change its name or locality, and the
changed version would be shown under the earlier approval.

**History is its own table.** `review_events` (section 3.9) belongs to
verifications and listings and stores status transitions. Directory edits
need field-by-field before-and-after values, so they get
`directory_events`. It has a `sequence` column because changes in one
transaction share a timestamp and would otherwise come back in random
order.

**Sample rows were retired, not just hidden.** The five development
samples from Phase 2 were invented. The `retire-samples` command deletes
the ones nobody chose and switches off (and keeps) the ones a member had
saved, so no member's data is deleted without their action.

## 10. Design decisions in version 1.4

**No new tables for discovery.** `swipes`, `matches`, `conversations` and
`notifications` were designed in version 1.1 and already had the
constraints matching needs. Phase 5 only added one index and relaxed one
column.

**A lock per pair, not a stricter isolation level.** Running every like at
`SERIALIZABLE` isolation would also prevent the lost match, but it makes
unrelated likes fail and retry under load. An advisory lock keyed on the
two people makes only requests about the same pair wait for each other.

**The notification rule is in the database.** Code already creates a match
notification only once, but a unique partial index guarantees it even if a
request is retried or code changes later.

**The match score is a record, not a promise.** It is stored as it was at
the moment of matching, so a later profile change does not rewrite history.
The current score is always worked out again when a profile is opened.

## 11. Design decisions in version 1.5

**Ownership is not permission to accommodate.** The listing authority
check asks one question: may this person offer this room to a student?
An owner proves ownership (and their identity). A tenant's genuine rental
agreement proves only that they rent the flat; it does not by itself
allow them to take someone in. So a reviewer approving a tenant must
record `tenant_permission_basis`: either the agreement itself permits
sharing (`AGREEMENT_PERMITS_SHARING`) or the landlord gave written
permission (`LANDLORD_PERMISSION`, which requires that document). The
agreement's end date is stored too, and the listing disappears from
public view once it passes. An agent needs identity verification, the
owner's written authorisation, and confirmation from the owner, whom
Roomie contacts directly.

**No new tables for photos or interest.** `listing_images` and
`listing_interests` existed since version 1.1; Phase 6 added the columns
they were missing. Profile photos use the existing
`student_profiles.profile_photo_key`.

**History is append-only.** `listing_changes` and `review_events` are
never updated or deleted, so what a creator changed and what a reviewer
decided can always be reconstructed.

**Nothing is approved automatically.** Uploading evidence changes nothing
by itself; submitting puts the listing in the review queue; only an
administrator can set `moderation_status`. The API never accepts a
status from a creator.
